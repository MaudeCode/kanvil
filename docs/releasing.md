# Releases

PRs and `main` pushes run `.github/workflows/ci.yml`. `main` pushes also publish an [experimental build](#experimental-builds). Independent suites and browser/native/Docker matrices run in parallel; only jobs consuming build artifacts wait for the build. The always-running `Checks` status requires every suite to succeed. Releases are dispatched for a version and a `main` commit and call that workflow on that commit, reusing the verification its push run already passed; the `vX.Y.Z` tag is created last, after everything published. Publishing jobs have registry write permissions; PR checks have read-only repository access, apart from CI's `release-freeze` job, which may only set the `release-freeze` commit status.

The public npm application package is `@maudecode/kanvil`; the workspace root and internal packages remain private. The release version supplies npm, Docker, and iOS: `v1.2.3` publishes `@maudecode/kanvil@1.2.3`, `ghcr.io/maudecode/kanvil:1.2.3`, and Kanvil 1.2.3 on TestFlight. The server build embeds that same version for Administration, public instance info, OpenAPI, and MCP. Installed artifacts need no Git checkout or release environment variables. No `package.json` version bump is needed. PR and local builds use the development version in `package.json`; custom Docker builds pass `--build-arg KANVIL_VERSION=X.Y.Z` to stamp the server and image label together.

## Publish a version

1. Merge the intended changes to `main` through a reviewed PR with green `Checks`.
2. Dispatch `.github/workflows/release.yml` on `main` with the version and, optionally, the commit you inspected, from the GitHub Scheduler's Releases page or `gh workflow run release.yml --repo MaudeCode/kanvil --ref main -f tag=vX.Y.Z -f sha="$(git rev-parse origin/main)"`. Without `sha`, the release is of `main`'s head when the run started; with it, the release is of that commit, which may be any `main` commit after the last release whose `.github` workflows match `main`'s. Every job builds and publishes the commit preflight resolved, whatever is merged while it runs. Dispatching authorizes public publication. Do not push the tag yourself; the workflow creates it.
3. Check the run titled `Release vX.Y.Z`. Its first job, the shared `release-preflight` action from `MaudeCode/.github`, rejects a run that is not a dispatch on `main`, a given `sha` that is not on `main` after the last release or whose workflow files differ from `main`'s (GitHub refuses the workflow's token that tags such a commit), a malformed or existing tag, and a version that does not come after every existing `vX.Y.Z` tag. It then looks up the `Checks` job of `ci.yml`'s push run on that commit. If it passed, the release reuses it and runs only CI's `Build web and npm artifacts`, `Installed npm package` and `Docker` jobs, which build and test the tarball and images it publishes under the release version. If that run failed, is still running, or never ran, the release runs the whole CI workflow on the commit itself; it never waits for the push run. The build rejects prerelease versions and `v0.0.0` before anything publishes. The last job, needing every publisher, creates the annotated tag `vX.Y.Z` (`Kanvil X.Y.Z`) at that commit with the shared `release-tag` action and then the GitHub Release. Repository rules keep the tag immutable once created. While the release runs, its `freeze` job fails the `release-freeze` commit status on every open PR that changes a `.github/workflows` file, and CI's `release-freeze` job does the same for a PR opened or pushed mid-release, because GitHub refuses the workflow's token that tags a commit whose workflow files differ from `main`'s. Its last job, `thaw`, passes the status again however the release ended. Every other PR carries a passing `release-freeze` status; listing it as a required status check on `main` is what blocks the merge.
4. Verify `npm view @maudecode/kanvil@X.Y.Z dist.integrity` and `docker buildx imagetools inspect ghcr.io/maudecode/kanvil:X.Y.Z`. The image includes Linux amd64 and arm64. Confirm anonymous Docker pulls work, check the TestFlight job's summary for the exact iOS version/build in Apple's `VALID` state, and check the GitHub Release for the tag and its automatically generated notes.

The workflow publishes the exact npm tarball installed by CI to the `latest` dist-tag, while separate amd64/arm64 publishers push the exact image archives tested by CI. Docker builds and restoration tests run on matching native runners; release publishing does not rebuild or emulate either image. A final Docker manifest job joins those immutable digests under `ghcr.io/maudecode/kanvil:X.Y.Z` and `:latest`. Stable and experimental builds share this publisher, `.github/workflows/publish-images.yml`. Stable releases only; prerelease versions are rejected. Preflight refuses a version that does not come after every existing `vX.Y.Z` tag, so a release never moves `latest` backward.

A failed release leaves no tag. For a flaky step, rerun the failed jobs of the same run. If the cause needs a fix and nothing published yet, merge the fix and dispatch the same version from the new commit. If something already published under that version from a commit that has since changed, release the next version. Every publisher accepts what an earlier attempt published from the same commit and refuses anything else:

- npm accepts an existing version only when its SHA-512 integrity matches the tarball CI just built and tested; different bytes fail and require a new version.
- Docker keeps an existing `X.Y.Z-amd64`, `X.Y.Z-arm64`, or `X.Y.Z` name whose image labels give the same commit and version, and fails on one from any other commit (`scripts/release-publish.ts`). The rerun moves `latest` to the same digest again.
- iOS starts only after npm and Docker succeed for the run's commit, because TestFlight records no source commit. A rerun uploads that commit again as the next build number of the same version; iOS build numbers increase across every version of the app and never restart, so an upload can't match an earlier version's build.

Publication is not atomic across npm, GHCR, and Apple. Never reuse a version for changed bytes.

After npm publication, the Docker manifest job, and Apple processing all succeed, the final job creates the `vX.Y.Z` tag and a GitHub Release for it with an automatically generated title and release notes. Only this job has repository contents write permission. Rerunning it keeps a tag that already names the commit, fails on one that names another, and preserves an existing release and its notes.

The iOS publisher is `.github/workflows/testflight.yml` on an ephemeral hosted Xcode 27 runner. It keeps only Kanvil's own steps: Expo's native project, the app target's signing settings, the archive, and the checks of its embedded bundle and native fixes. Signing, the build number, the export, IPA verification and the upload come from the shared `ios-signing`, `ios-build-number` and `ios-publish` actions in `MaudeCode/.github` (its `IOS.md`), pinned by commit. They read the organisation secrets `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_PRIVATE_KEY`, `IOS_DISTRIBUTION_CERTIFICATE_P12_BASE64` and `IOS_DISTRIBUTION_CERTIFICATE_PASSWORD`, and the team comes from the certificate. A secret of the same name in the repository or the `testflight` environment overrides the organisation's, so keep none there. The upload runs in the `testflight` environment, restricted to `main`, where release runs are dispatched. A re-run for the same version and commit gets the build number it already uploaded and uploads nothing twice. Dispatching `testflight.yml` with a version and a commit is a dry run: it builds, signs and verifies the IPA without the environment and without uploading. The Apple account must contain the `dev.kil.kanvil` app record and an active App Store profile issued for the distribution certificate. Configure its TestFlight information and an internal testing group with automatic build distribution in App Store Connect. It retains no public IPA artifact. Android store publishing remains separate.

## Experimental builds

Every push to `main` also publishes an experimental build once CI passes on that exact commit. `.github/workflows/experimental.yml` runs when a CI run finishes. It publishes only a successful `push` run of this repository's `main` whose commit is still on `main`; pull requests, forks, other branches, release runs, and failed or cancelled runs publish nothing. Each `main` commit runs CI in its own concurrency group, so a newer push never cancels or replaces an older commit's verification or publication.

An experimental build of commit `SHA` (the full 40-character commit) has the version `0.0.0-experimental.gSHA` in Administration, public instance info, OpenAPI, MCP, and the image's `org.opencontainers.image.version` label; `org.opencontainers.image.revision` is `SHA`. CI builds and tests it with that identity (`KANVIL_RELEASE_CHANNEL=experimental` in `scripts/release-version.ts`), and publishing reuses the exact native images CI tested:

- `ghcr.io/maudecode/kanvil:experimental-SHA-amd64` and `-arm64`, then the multi-platform `ghcr.io/maudecode/kanvil:experimental-SHA`. These names are immutable.
- A Git tag and GitHub prerelease named `experimental-SHA`, pinned to `SHA`, created only after both architectures and the multi-platform manifest are published. It is never marked latest; its notes give the source commit, image, and manifest digest after the generated change list.
- `ghcr.io/maudecode/kanvil:experimental`, the opt-in rolling alias. It moves to the newest announced experimental build on `main`'s first-parent history and never to an older commit, so builds that finish out of order and reruns of old runs cannot move it backward. Only this step is serialized.

Experimental tags start with a letter, so tools that read numeric Docker tags as versions, such as Renovate, never treat them as upgrades from a stable release; CI's `Renovate tag selection` job checks this with Renovate itself. Experimental builds never publish npm packages or move npm dist-tags, `latest`, version tags, or the latest GitHub release.

Reruns are safe. `scripts/release-publish.ts` keeps an existing image, manifest, tag, or release that names the same commit and version, and fails on one that names anything else rather than replacing it. If one architecture fails to publish, rerun the failed jobs of the `Experimental` run; they reuse the images CI tested and the architecture already published. If only the alias move fails, rerun it, or let the next `main` commit's run move the alias; it always selects the newest published build.

Tag creation and package publication are separate from deploying to any running instance. Operators choose when to upgrade using [self-hosting](self-hosting.md).
