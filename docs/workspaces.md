# Workspaces and project access

A Kanvil instance hosts accounts and deployment settings. Workspaces group projects and have their own name, URL key, and members. Personal settings belong to the account. Instance administrators can administer every workspace and project; workspace administrators cannot administer the instance or other workspaces.

Every workspace starts with the Read only, Can edit, and Admin roles. Administrators add custom roles under Workspace settings → Roles, each a chosen set of actions: edit tickets, delete tickets, manage projects, members, invitations, sharing, or the workspace. Members get any of them through the same member editor, on the workspace or on one project. Nobody grants an action their own role lacks, only administrators grant Admin, and a role held by anyone is deleted only after choosing the role its members move to. Clients show what the server reports a role allows, never what its name suggests. Workspace-visible projects inherit workspace roles. Private projects require explicit project membership, except that workspace administrators can manage all projects in their workspace; a custom role never reaches private projects through the workspace. Explicit project roles override inherited roles, except for workspace administrators. A person with only project membership can see that project and its workspace identity without receiving workspace-wide access.

Workspace administrators can also invite an email address that has no access yet. An invitation fixes its role and covers either the whole workspace or selected projects, and its link works once, before it expires, for the account with that email. Kanvil account emails are set by instance administrators or verified by the OIDC provider, and people cannot change their own, so the email match identifies the recipient. Accepting checks again that the sender still administers the workspace, grants only the invited access to projects that still exist, and keeps any higher role the person already has. Invitations follow the instance's sign-in policy: they never create an account or open registration. The link is emailed when SMTP is configured and can always be copied from the dialog shown after sending; resending replaces it.

A project moves to another workspace only when the caller administers both. Direct project members keep their roles; access inherited from the old workspace ends and the destination's applies, which the move preview lists person by person. See [the API reference](api.md#project-lifecycle).

Every workspace has one owner, an active administrator. The owner, or an instance administrator, transfers ownership to another active administrator and deletes the workspace; the previous owner stays an administrator. The owner cannot be removed, demoted, disabled, or have their account deleted until ownership moves, so a workspace never loses its owner silently. Deleting a workspace needs a sign-in within the last 15 minutes and the typed URL key, lists every project and what goes with it first, and refuses while any ticket is claimed. Its projects are deleted as project deletion does, its memberships, invitations, and shared labels go, and accounts stay. See [the API reference](api.md#workspace-ownership-and-deletion).

When ownership was introduced, each existing workspace went to its earliest-created active administrator member, ties broken by account ID. A workspace without one has no owner until an instance administrator transfers it to an active administrator.

Removing workspace membership also removes that person's explicit memberships in the workspace's projects. Keep at least one workspace administrator. Project-scoped API keys remain bounded to their configured projects and cannot administer an entire workspace. Ticket and project prefixes remain unique across the instance. A project administrator can change a prefix and move tickets between writable projects of one workspace; earlier prefixes stay reserved and earlier keys keep resolving, so existing links and key-based API lookups keep working without reaching past current access.

Existing projects are assigned to a default workspace and remain private. Existing project membership is retained; only instance administrators gain workspace administration automatically. Existing API calls that omit a workspace choose an accessible writable workspace; when none exists, project creation creates a personal workspace for the caller. New web-created projects select their workspace explicitly and offer workspace or private access.

Workspace operations use the same operation registry, authorization, transaction lock, idempotency receipts, and HTTP/MCP implementations as projects. Realtime visibility continues to derive from accessible projects, so revoked membership stops event delivery. Workspace changes invalidate project consumers through project events; an empty workspace also refreshes in browser queries on focus.

Workspace administrators can define labels every project in the workspace uses, beside each project's own labels. Projects show workspace labels read-only in their label settings; renaming or deleting one updates every project's tickets and saved views together. See [the API reference](api.md) for conflict and adoption rules.

Anyone who can read a project can export its tickets as JSON from the project's settings. Workspace writers import such a file, or a Linear team, a Jira, Plane, or Kaneo project, or a Trello or PLANKA board, into a new project from the workspace's settings. For a tracker, connect with what it asks for (an API key or token, a site address, or a PLANKA password), which is used only while the form reads the source and is never saved, then pick the team, project, or board and whether to include comments. The preview lists what maps, what changes, and what the import leaves out before anything is written, and the import continues in the background, resuming after a restart. See [Export and import](api.md#export-and-import).

Project icons can use a bundled, searchable open-source icon collection or a normalized image upload. Uploaded bytes use the existing blob storage adapter and authenticated project access. Referenced icons must remain excluded from orphan cleanup, and backup/restore retains them with other blob objects.

## Verification

- Upgrade populated databases without widening private project access or changing ticket identifiers.
- Test workspace and private-project isolation, inherited versus explicit roles, scoped API keys, removal, last-admin guards, and idempotent writes through the shared domain.
- Exercise workspace discovery through HTTP and MCP and access revocation through realtime replay and image routes.
- Test shared label catalogs, access-filtered counts, cross-project renames and deletions, claims, and same-name adoption.
- Test ownership transfer, owner removal, demotion, and account-disable guards, concurrent transfer and removal, and workspace deletion previews, blockers, recent sign-in, and tombstones.
- Test invitation creation, resend, revocation, expiry, email mismatch, sender demotion, concurrent acceptance, and the acceptance page.
- Test custom roles: seeded roles on upgraded memberships, granular actions, credential ceilings, grants beyond the actor, immediate revocation, stale edits, reserved names, deletion with reassignment, private projects, and owner and last-administrator guards.
- Test workspace switching, deep links, settings navigation, member search and role changes, icon selection/upload/removal, and account administration in browser workflows.
- Review light/dark desktop and phone layouts with real content. Keep publication separate from local verification.
